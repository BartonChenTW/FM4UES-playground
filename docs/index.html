What is a foundation model, in modeller's terms?

In energy modelling you usually calibrate a model to your own data: you fit a regression of demand on temperature, or train a random forest on one building portfolio. The model knows only what your dataset contains.

A foundation model (FM) is trained once, by someone else, on a very large and varied collection of data: thousands of time series from many domains, millions of synthetic tables, or hundreds of millions of image–caption pairs. From that it learns general patterns such as daily and weekly cycles, how table columns usually relate to a target, or what a forest looks like from above. You then apply it to your problem, often with no training at all.

Three ways to use an FM (all shown in this playground)
  • Zero-shot. Give it your input and read the answer. Example: Chronos forecasts Swiss demand from its history alone (Module 1).
  • In-context learning. Give it a few labelled examples together with the question; its weights do not change. Example: TabPFN reads your known buildings and predicts the unknown ones (Module 2).
  • Frozen encoder + small model. Use the FM only to turn raw data into an embedding (a vector of numbers), then fit a simple model such as a logistic regression on top. Example: the CLIP linear probe (Module 3).

A fourth way, fine-tuning (continuing to train the FM on your data), is more powerful but also more expensive and easier to get wrong. It is not covered here yet.

Where FMs fit in an energy modelling workflow

FMs rarely replace your energy system model. They are most useful in the data preparation layer: they produce the forecasts, the missing attributes and the classifications that your optimisation, dispatch or urban building energy model (UBEM) needs as input.

The recipe every module follows

The specific models will change quickly. The way you test them should not. Each notebook follows the same five steps, and you can use them for any new FM you want to try.

Frame the taskWhat goes in, what comes out, and at what horizon or resolution.
Load real dataPublic, cached on first run. Look at it before modelling it.
Set a baseline"Same as yesterday", "always the average". The FM has to beat these.
Run the FMZero-shot, in-context, or frozen encoder. Usually 3–5 lines of code.
Evaluate honestlyA whole year, cross-validation, calibration, runtime. Not one good-looking plot.

Set up your machine

You need Miniconda, an internet connection on the first run, and ideally an NVIDIA GPU with driver 570 or newer. Everything also runs on a CPU, just more slowly (Module 1: about 90 s instead of 45 s). 

git clone https://github.com/BartonChenTW/FM4UES-playground.git
cd FM4UES-playground

# 1. Create the environment (PyTorch with CUDA 12.8 + all packages, ~5 GB)
conda env create -f environment.yml
conda activate fm4ues

# 2. Make it available as a Jupyter kernel
python -m ipykernel install --user --name fm4ues --display-name "Python (fm4ues)"

# 3. Check the GPU (should print True and the GPU name)
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"

Then open a notebook in VS Code or JupyterLab, choose the Python (fm4ues) kernel and run all cells. Data (a few MB) goes to data/cache/. Model weights (about 4.5 GB for all three modules) go to the Hugging Face cache. To keep the environment and caches on another drive, see the README.

No GPU, or just reading?

All notebooks are committed with their outputs, so you can read every plot and table on GitHub without running anything. The pages on this site walk through the same content and add context for energy modellers.
